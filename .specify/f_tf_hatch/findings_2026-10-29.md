## One-paragraph state

f_tf_hatch was redesigned from a lattice-of-marks renderer (v1, archived) into a per-pixel
**streamline / LIC renderer** whose job is to make a tensor's coherence and topology visible.
The design passed offline tests (tier 1, 11/11) and the GPU codeboxes match the NumPy mirror
exactly on constant-axis fields (tier 2, E1/E2/E3 all exact). `definition.py` was rewritten and
the patcher rebuilt, so it is live in Max. **On a live camera tensor the output is wrong:
little axis-aligned rectangles on a grid, not strokes along contours. The mirror does NOT
reproduce this at Matt's exact settings, so it is a GPU / live-pipeline defect or a tensor
effect the mirror lacks. That is the open problem.**

## What the module is (design, decided with Matt)

- Input: `f_tf_tensormap` outlet 0 (raw tensor). Three jit.gl.pix stages:
  - **E1** decode + presence -> aux `(cos a, sin a, coherence, presence)` (`unsigned_nearest`).
  - **E2** the march: N = 16 steps each direction, one pass; sign continuity by dot-product
    alignment; noise = sparse impulses (a lattice cell is lit when its hash < fill) in WORLD
    coordinates; brightness = lit cells crossed (acc * step / cell_px); a path that leaves the
    frame stops contributing; coherence enters ONLY as direction persistence:
    `d = normalize(w*axis + (1-w)*random_unit_vector)`, `w = coherence^0.5`.
  - **E3** contrast gain 0.6-2.0, `line_hard` threshold, times presence, encode, bypass.
- Dials: Length (`reach`), Grain, Density, Contrast, Line (`line_hard`), Strength, Floor
  (`structure_floor`), Offset (`angle_offset`), bypass. `reach`/`line_hard` because `length`
  and `line` are GenExpr operator names.
- Decisions Matt made: coherence is NOT a stroke-length/shape dial but direction persistence
  (scatter); dense LIC noise read as "contour-streaked noise", sparse impulses read as
  hatching; tier 3 is judged live on the built module, no scratch patches (standing rule
  2026-10-26).

3. Grain 0.62, Length 0.63, Density 1.0 (after the hash change, presumably reopened): still

Matt's reading: "we're not getting any stroke orientation along contours or streamlines at
all; grain is just little rectangles on a grid; increasing that dial makes them bigger until
we hit some mean value." He also asked, fairly: "aren't we building a LIC here?" (yes, with

any effect".

### What the mirror says (`spike/camera_like.py`, half-size, Matt's exact settings)
Oriented strokes follow rings / spirals / stripes; speckle only where the tensor is noise;
no rectangles. Sheet: `~/Desktop/hatch_camera_like.png` (A shipped, B persist OFF, C offset 0).
So the defect is not the design as mirrored. Coherence of the synthetic small-window tensor
was mean 0.74, p25 0.47: the real camera tensor may be much lower (unmeasured).

### Dial effects in the mirror (`spike/dial_effects.py`)
- **Strength: zero effect (by design).** v2 decode uses only ratios (axis, coherence);
  presence reads the raw encoded trace; Strength only feeds the `eps_trace` zero guard.
  The dial is dead. Recommendation: remove it (Matt has not decided).
- Offset: large effect (~48% of pixels change). Live "no effect" is NOT explained.
- Contrast: 0 dims clearly (27% pixels); 0.5 -> 1 nearly dead (strokes saturate: 10%).
- Line: ~10% pixels (edge sharpening only; sparse strokes are already near binary).
- Grain: strong at every value; mean brightness varies a lot (0.46 / 0.30 / 0.18 at
  0.42 / 0.57 / 0.69). Direction note: **low Grain = fine/thin, high = coarse/thick**
  (cells per frame height = 2^((1-grain)*6+3)); the dial hint said the reverse until fixed.

## Hypotheses for the rectangles, ranked, with the discriminating test

1. **The GPU `hash13` random direction is degenerate or biased** (e.g. concentrated near
   angle 0, so low-coherence paths drift horizontally; horizontal paths through lit cells
   sweep exactly such bars). NEVER tested on the GPU: all GPU parity used coherence-1 fields,
   where the random term drops out (weight 0). Test: the new `test_hash13_gpu_matches_numpy_and_is_isotropic`
   and `test_stage_e2_matches_on_incoherent_fields` (written, not run).
2. **The live camera tensor really is blocky/axis-aligned** (video compression macroblocks,
   Smooth, Radius 1.26 px). Test: capture the tensor texture or E1 aux from the live patch
   (or feed the bench a saved camera frame's tensor) and look at coherence/axis maps; run
   the mirror on that frame.
3. **Stages don't re-render when only a downstream/own Param changes** (E1/E3 dials "no
   effect"): jit.gl.pix chains render on texture arrival; a Param message alone may not
   re-render until the next frame. Matt's source is a live camera, so frames do flow, which
   argues against this, but it is unchecked. The contract bench (`tests/contracts/bench_modules.py`)
   only checks param READ-BACK on the pix attribute, not that the output changes.
4. **Param delivery to E1/E3** (the dials that "don't work" are exactly the E1 and E3
   targets: strength, offset / contrast, line_hard) vs E2 (reach, grain, density) which do.
   Wiring in the built patcher looks identical for all three stages (attrui -> pix), and v1
   delivered density to E3 fine. Worth one bench that sets each dial in the shipped patcher
   and diffs the output.
5. Something 1080p-specific in E2 (precision of `px/wpx`, loop, `floor(x0)` hash inputs).
   The 64x64 parity passes exactly; no geometry test exists at 1080p.

Cheapest decisive next step: run the bench once (Vsynth/Max live session CLOSED so the cost
reading is clean): `tests/bench.sh -q tests/modules/tf_hatch/bench_tf_hatch.py`. That runs
hypothesis-1 tests and the partial-coherence parity, and re-measures cost. Then, if it still
passes, add a 1080p geometry test with a swirl/stripe tensor and a mixed-coherence field.

## Design question for Matt (not yet answered)

We ARE building LIC, with one deviation: a textbook LIC follows the field strictly; ours mixes
a per-step random unit vector weighted by (1 - coherence^0.5) so isotropic regions render as
grain instead of the atan2(0,0) "vertical axis" trap. On a low-coherence real tensor that
random part dominates. Options (none built):
- **A** steeper persistence curve, e.g. `smoothstep(0.1, 0.5, coherence)`.
- **B** a `Persist` dial (OQ1 reserved this).
- **C** both.
- **D** strict LIC (persist off: tier-1 mutation shows streaks everywhere, worm-like curls in
  noise: the "contour-streaked noise" look Matt rejected) with **coherence setting integration
  length** instead of direction scatter, so low-coherence pixels get short strokes that still
  point along the local axis. This reverses Matt's earlier "not stroke length" decision and
  needs his OK; offered as the honest-LIC variant to judge live.
The mirror comparison of A / D vs shipped on a camera-like tensor was offered, not done.

## Lessons / gotchas learned this session (add to the skills if they hold)

- **`sin(ix*127.1 + iy*311.7)*43758` is not a usable hash on the GPU at 1080p lattice
  indices** (argument up to ~5e4): precision collapses, the lit pattern clumps and flips with
  0.01 changes of the cell size. NumPy and the GPU already disagreed on 10% of cells at 64x64.
  Replaced by Hoskins' sin-free `hash12` / `hash13` (every intermediate < ~1e3). GPU = NumPy
  to 0.05% of cells. The bench's E2 reference still uses the GPU's own `hash12` table so
  parity is about geometry, not the hash.
- **`norm` is texel-centred: `(i + 0.5)/dim` (`tests/lib/gpu_sim.py`, `jxf.py`).** A "fix" to
  `norm*(dim-1)+0.5` made parity worse (20% mismatch). `cell` is `norm*(dim-1)`: do not use it
  for pixel positions. The 8.7% mismatch in the cost spike was the hash, not the start point.
- GenExpr reserved/hazard names hit here: `length`, `line` (operators; Params renamed
  `reach`, `line_hard`), `cell` (even as a function argument name). Component access must be
  inline on `sample()`/`nearest()`.
- A bench run is ~2-3 minutes and the Desktop Commander relay times out at 60 s: start it
  with `(nohup tests/bench.sh -q FILE > tests/logs/NAME.out 2>&1 &)` and read
  `tests/logs/latest-bench` later. `-q` prints only pass/fail; the numbers are in the full log.
- Bench cost readings are contaminated by other GPU work (a live Vsynth session): E1/E3 at
  the "floor" jumped 0.73 -> 1.2 ms.
- The first bench run caught real mistakes only because it exercised the shipped codebox at
  a different size/coherence than the spike; keep adding a case per behaviour the live look
  exposes.
