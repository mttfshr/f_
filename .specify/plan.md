### Infrastructure: f_util_matrix
Working implementation exists; refinement blocked on the UI density discovery phase above. Don't touch until that closes.

**2026-07-29 — reframed as a library-wide mod-texture assignment convention.** Long design discussion, concluded. `ideas/f_util_mod_texture.md` rewritten as the conclusion (file retitled; the original "externalized mod texture util" framing was investigated and **rejected** — assignment cannot leave the module, since params live in the shader with hardcoded use sites, and an external util would only shadow the in-module accumulation while creating two sources of truth for the weights and fragmenting preset recall). Conclusion: **2 mod texture inlets as the working default per module, with per-param weighted accumulation in the codebox** (`param_eff = clamp(param + a*amt_a + b*amt_b, lo, hi)`) — generalizing what `f_masonry` already does rather than inventing new machinery. Key verified findings: (1) `definition.py`'s existing `mod_inlets` key already *is* the self-declaration mechanism the discussion spent a long time theorizing about — what may still need adding is a modulatable-params declaration so codegen knows which `_mod_amt_` pairs to emit; (2) `f_masonry` is the **wrong template to generalize from** — its three inlets are three distinct *coordinate spaces* (slot identity / intra-brick / screen), which it affords only because of its slot-course geometry; most modules afford one, discrete-item generators plausibly two, so inlet count falls out of module geometry rather than being a number to standardize on; (3) `package/javascript/f_util_matrix_grid.js` is already generic, data-driven (`params <names…>`), scrollable, and has a strip mode — further along than "unwieldy flat table" suggested, though `NUM_SOURCES=3` is hardcoded and masonry feeds it ~14 phantom cells that aren't wired in the codebox. **Explicit decision: don't bank on any existing UI** — settle the `definition.py` contract and codegen first, ship on one simple module with minimal UI, design the real UI once it's been used. Rollout is cheaper than feared: `f_sirds`/`f_vf_advect`/`f_vf_seeds` each have their own build script and are regenerable through it, so the work is teaching four builders one pattern; `f_masonry` (no build script, already has a working version) is arguably last to touch, not first. Rejected branches recorded in the idea file so they aren't re-litigated: external util (three separate justifications, all fail), channel muxing into RGBA, dynamic inlet/outlet counts. **Same-session clarification, important:** *scalar* param modulation and *texture* param modulation are different mechanisms and were initially conflated. Verified against Kevin's `vs_displacement` (`Vsynth/patchers/vs_displacement.maxpat`): texture-modulating a param requires a **triple** — base scalar (`param zoom 1.`), paired mod-depth scalar (`param zoom_m 0.`), and a bound texture inlet — not a boolean "modulatable" flag. Two blocking consequences: (a) **Kevin's mod textures are bipolar** (`scale 0. 1. -1. 1.` before the depth multiply, so 0.5 grey = neutral, matching the `f_vf_` convention) while **`f_masonry` is unipolar** (raw `sample().r`, black = neutral) — the library carries two incompatible conventions and this must be settled before anything is built, since it changes every accumulation line; (b) **Kevin's model is 1 texture inlet per param**, which is canonical Vsynth but doesn't scale (masonry's 13 params would need 13 inlets — precisely why it went to shared inlets + a matrix), so the shared-inlet + assignment approach is a **deliberate break from Vsynth convention, not a refinement** — and per Matt the motivating reason is that `f_` modules simply have far more params than Kevin's (his `vs_displacement` modulates four things and has four mod inlets; masonry's 13 would need 13, which is unpatchable), so the break is forced by scaling pressure rather than chosen. That reframes the question from "should we break convention" (settled: yes) to "what replaces 1:1 binding, and how much of Kevin's convention — naming, depth-param shape, bipolar remap — should be preserved anyway" (default assumption: preserve everything except the binding model). **Caution recorded:** masonry's mod inlets were developed in isolation without reference to Kevin's conventions (Matt's own assessment) — which is how the unipolar divergence got in — so masonry is evidence about scaling pressure but **not** a source of convention authority; current leaning is bipolar. Not specced, not scheduled.

**2026-07-29, same session — possible alternative that may supersede the above: `ideas/named_mod_textures.md`.** UNVERIFIED HYPOTHESIS, nothing scratch-tested. Idea: a texture in Max *is* already a named message (selector `jit_gl_texture` + name symbol), and Kevin already routes on it — **verified**, `vs_displacement`'s control inlet opens with `routepass enable jit_gl_texture jit_matrix → route angle zoom x y xm ym rotm zm kmode mmode`. So tag a texture stream upstream with `[prepend zoom_tex]`, send it into a *single shared* mod inlet, and demultiplex inside the module with `route` out to N `jit.gl.pix` inlets. Max inlets accept many incoming cables, so the "one texture per inlet" constraint only bites for *untagged* streams (last-write-wins) — tagged, several coexist on one inlet. If it holds: **one mod inlet per module regardless of param count**, Kevin's 1:1 binding preserved *internally* (so it's an extension of Vsynth convention, not a break), no matrix, no assignment UI, depth params untouched and orthogonal. Trade-offs: assignment legibility moves upstream into the patch (can't read a module's routing by looking at the module), and it resurrects a *legitimate* tiny util — a name-picker (menu → `prepend`) that never touches the texture and so dodges every objection that killed the router version. **Six scratch tests written up in the idea file (T1–T6), all untested; T1 (prepend/route texture round-trip) is load-bearing — run it first, it's cheap, and until it passes this is speculation.** Note T6 is a real design wrinkle: a tagged texture's selector becomes `foo`, not `jit_gl_texture`, so it won't match Kevin's existing `routepass` stage — reshapes the plumbing, doesn't kill the idea. Findings that survive either way and must not be lost if this supersedes the matrix approach: the scalar-vs-texture **triple**, the unresolved unipolar/bipolar divergence, `mod_inlets` as the declaration site, and masonry-is-not-convention-authority.

- **`f_loop_to_cycle`** — NEW 2026-07-29, `ideas/f_loop_to_cycle.md`. Treat a looped video clip as a WFG-like phase signal: frame-index / N as phase (0–1, wrapping), so WFG-domain operations (phase modulation, phase offset, frequency/rate scaling) apply to loop playback. Named target use case: drive `f_masonry`'s brick modulation so each brick samples a *different frame* of the same loop. Central unresolved question: whether frames can be GPU-resident and indexable (making phase-mod a per-pixel `jit.gl.pix` operation, matching how WFG phase-mod already works) or whether Max/Vsynth only offers CPU-side sequential playback with seek — architecturally very different, and only the former supports the per-brick many-simultaneous-reads case. Second question surfaced same session: a per-pixel phase-mod texture constantly lands on *non-integer* frame positions, which a continuous WFG never does — so between-frame state must be defined (interpolate/blend, interlace/dither, or floor), and that choice is itself gated on the GPU-resident question since seek-based playback likely can't interpolate at all. Not specced, not scheduled.
