# f_ Module Preflight

Why this exists: every module-readiness check in this repo grew up separately
-- `build/drift.py`, `tests/run.sh`, `generate_launch.py --check`, the
helpfile `pending`/`stale` tracking in `build/spec.md`, and the one-off
"packaging bar" invented for `f_a_ripple` and reused for `f_a_decorrelate`.
None of them check whether the helpfile actually renders without clipping,
or whether its text says anything true and specific about the module's
purpose -- that gap surfaced 2026-10-13 when 17 helpfiles (14 generated by
`build/make_missing_helpfiles.py`, 3 hand-corrected) turned out to have
every module bpatcher hardcoded to 154x91 -- `f_vf_vortex`'s own footprint,
copied into the canonical template and never revisited -- cropping almost
every module whose UI is bigger. This checklist is the consolidation: run
it instead of inventing a bar per module.

**This is a per-module gate, not the packaging-readiness project.**
Library-wide release readiness (license, icon, Package Manager submission)
lives in `.specify/packaging/tasks.md` -- separate and mostly Matt's own
calls (asking Kevin, picking an icon). This skill is "is this one module
actually finished," which that project assumes as a precondition.

---

## Part 1: Mechanical checks (scriptable, no judgment)

Run these and expect green. A red here means the module isn't done --
don't override, fix it.

- [ ] **Drift.** `build/py.sh build/drift.py -v f_name` -- the shipped
  patcher reproduces from `definition.py`, or the module is deliberately on
  the never-regenerate list (`.specify/plan.md` Build system section) with a
  reason, or it has an `out_of_scope` entry in `tests/drift_baseline.json`
  with a reason mirroring an existing precedent (see `f_a_ripple`/
  `f_a_decorrelate`'s entries).
- [ ] **Test suite.** `tests/run.sh` green for anything that touches this
  module: its own `bench_*`/`test_*` files, `build_conventions`, and the
  full launch/menu suite.
- [ ] **Menu + launcher registration.** `build/generate_menu.py` and
  `build/generate_launch.py --check` both pass; `tests/test_launch.py`
  green. The module appears once, in the right category, clickable iff it
  has a helpfile.
- [ ] **README row.** One line in the README Patches table, <=110 chars,
  correct category, honest about status (a module that's unverified,
  paused-mid-retool, or unfinished gets its warning mark here, not just in
  `.specify/`).
- [ ] **Bypass convention.** If the module has a bypass, it's wired through
  a codebox `Param bypass_gate` mixing to the kind-appropriate neutral
  (source for textures, 0.5/0.5 for vecfields) -- never the native
  `@bypass`, which skips the shader and silently flips secondary outlets.
  See `skills/vsynth-bpatcher/SKILL.md` "Native bypass caveat."
- [ ] **`docs/f-reference/f_name.md` exists** and matches the module's
  current, actual, shipped state -- not a stale draft from an earlier
  design. This is the upstream synthesis the helpfile draws from
  (`skills/f-helpfile/SKILL.md`'s prerequisite); if it's missing or stale,
  writing/fixing it *is* the next task, not a thing to skip past.
- [ ] **Helpfile exists and isn't cropped.** Compare the helpfile's module
  bpatcher box (`d-4`'s `patching_rect` width/height) against the module's
  real presentation-view footprint (the bounding box of its
  `presentation: true` boxes' `presentation_rect`s, read straight from the
  shipped `.maxpat`). The box must be at least that size. **No script does
  this yet** -- the 2026-10-13 fix was a one-off repair script
  (`/tmp/fix_helpfile_sizes.py`, not in the repo); worth promoting to a real
  `build/check_helpfile_fit.py` if this keeps recurring. Until then, check
  by hand or ask for the comparison to be run.

## Part 2: Judgment gate (open the module, read the helpfile, decide)

No script passes this for you. A module can be mechanically green and still
not be done.

- [ ] **Open the module + its helpfile in Max.** Confirm the demo wiring
  actually produces something sensible at defaults, nothing's clipped, no
  console errors.
- [ ] **The helpfile's digest line says what the module is *for*, not just
  what it *is*.** "Vecfield-driven chromatic streak" describes the
  mechanism; it doesn't say when you'd reach for this module over a
  neighboring one, or what effect it's chasing. Read `docs/f-reference/
  f_name.md`'s own framing and the module's `spec.md`/`plan.md` for the
  actual "why" -- don't invent one from the param list.
- [ ] **The signal-flow comments (recipe bubble, wiring) explain the
  module's actual role in a chain, not a generic "feed X into inlet Y."**
  If the module only makes sense as part of a specific pattern (e.g.
  `f_vf_potential` feeding `f_weave`'s scalar inlet for field-curved lines),
  say that -- a user patching it in cold gets nothing from "accumulates
  vecfield magnitude" alone.
- [ ] **Status caveats are carried through consistently.** A module marked
  unverified/paused/unfinished in `.specify/` or the README should say so,
  in the same words, in the helpfile digest -- not get a polished-sounding
  digest that reads as more finished than the project considers it.
- [ ] **References are real, not a placeholder.** `"See docs/f-reference/
  f_name.md"` alone is a stub. If the module's math/technique has a real
  citation, it belongs in both the doc and the helpfile summary
  (`skills/f-helpfile/SKILL.md`'s "docs/ References Convention").

## When this runs

- Before moving `.specify/f_name/` into `.specify/stable/f_name/`
  (`build/spec.md`'s stable-promotion lifecycle already names most of Part
  1's steps in sequence -- this just adds Part 2 as a required stop, not an
  afterthought).
- Before calling a module "packaging-ready" the way `f_a_ripple` and
  `f_a_decorrelate` were.
- Whenever asked "is this module actually done."

Don't run this as a batch sweep across many modules at once expecting to
clear Part 2 quickly -- that's exactly how the 17-helpfile content debt
accumulated. One module's "why" deserves a few real minutes, not a
templated sentence filled in from its param list.
